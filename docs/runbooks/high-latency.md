# Runbook: High Latency

**Алерт:** `HighLatencyP95` — p95 времени расчёта транзакции > 5с на протяжении 5 минут
**Приоритет по умолчанию:** P2. P1, если p95 продолжает расти или пользователи (симулированные) массово уходят в timeout.

## Симптомы

- Панель "Latency — p50/p95/p99" в Grafana — линии p95/p99 резко выше базовой (норма: сотни мс — единицы секунд, зависит от того, задействован ли Toxiproxy)
- Возможен рост `app_pending_transactions` — транзакции скапливаются быстрее, чем резолвятся

## Диагностика — строго по порядку, снизу вверх по стеку

### 1. Сеть

```bash
ping -c 5 10.10.10.12
mtr 10.10.10.12   # если стоит: sudo apt install mtr-tiny
```

Ищи потери пакетов и скачки RTT. Проверь также, не активна ли деградация
через Toxiproxy на прокси к БД или к конкретному провайдеру:

```bash
curl http://localhost:8474/proxies | python3 -m json.tool
```

Смотри поле `"toxics"` у каждого прокси — если непусто, там и причина.

### 2. База данных — самый частый источник latency

```sql
SELECT pid, now()-query_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC LIMIT 10;

SELECT * FROM pg_locks WHERE NOT granted;
```

Параллельно глянь дашборд `postgres_exporter` в Grafana:
```promql
pg_stat_database_numbackends{datname="shop"}
```
Растущее число соединений без роста RPS — признак того, что запросы
начали выполняться дольше и не успевают освобождать соединения.

### 3. Приложение — генератор и settlement-поток

```bash
tmux attach -t traffic-gen
```
Проверь пункт меню 4 "Статус" — в частности состояние circuit breaker
по каждому провайдеру. Latency расчёта транзакции напрямую зависит от
латентности вызова провайдера (settlement дожидается ответа от
`call_provider()`), так что:

```promql
app_provider_conversion_rate
app_provider_circuit_state
```

Если конкретный провайдер в состоянии `half_open` или недавно вышел из
`open` — это может объяснять локальный рост latency именно по нему.

### 4. Ресурсы самих ВМ

```promql
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
(1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100
```

В виртуалке легко упустить: сосед по хосту (другая ВМ) может отжирать
CPU host-а, и это будет выглядеть как "необъяснимая" latency без видимой
причины в самом приложении.

## Восстановление

- Toxiproxy с забытой латентностью/таймаутом → снять через меню
  `traffic_gen.py` → 3 → 12, либо вручную `DELETE` конкретного toxic
- Заблокированный запрос в БД → `SELECT pg_terminate_backend(<pid>);`
- Провайдер в `open` из-за реальной, а не тестовой деградации → дождись
  cooldown (по умолчанию 30 сек) и перехода в `half_open`, либо форсируй
  восстановление через toxiproxy_control.restore_provider()

## Эскалация

Если после исключения сети/БД/Toxiproxy/circuit breaker latency всё ещё
высокая — проверь, не совпало ли начало проблемы с каким-то деплоем/
изменением (см. `reconciliation-mismatch.md`, там же техника поиска
корреляции через Kibana). Если совпадения нет — эскалация на уровень
"нужен профайлинг приложения", в реальной системе это уже не runbook,
а полноценное расследование с APM.
