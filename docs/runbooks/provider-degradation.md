# Runbook: Provider Degradation

**Алерты:** `ProviderCircuitBreakerOpen` / `ProviderConversionLow` / `ProviderFailoverSpike`
**Приоритет по умолчанию:** P2 для одного провайдера. P1, если деградируют два и более одновременно (резко сокращает пропускную способность системы).

## Симптомы

- `app_provider_circuit_state{provider="X"}` = 2 (open) для конкретного провайдера
- `app_provider_conversion_rate{provider="X"}` резко упала
- Возможен всплеск `app_provider_failover_total` — трафик активно перебрасывается на других

## Важно понимать сразу

Circuit breaker **уже отреагировал автоматически** — новый трафик на
проблемного провайдера не идёт (или идёт малой пробной долей в `half_open`).
Это не экстренная ситуация в духе "всё падает прямо сейчас" — система
себя защитила сама. Задача — понять причину и решить, ждать
самовосстановления или вмешиваться.

## Диагностика

### 1. Это реальная деградация или мы сами её включили?

Первым делом исключи учебный сценарий:

```bash
tmux attach -t traffic-gen
# меню → 4. Статус
```

Проверь состояние в самом Toxiproxy:
```bash
curl http://localhost:8474/proxies/paycore   # или fastpay / cryptogate
```
Если `"enabled": false` или есть активные `toxics` — включена деградация в скрипте. Идём сразу в раздел "Восстановление".

### 2. Проверка реального ответа провайдера напрямую, в обход circuit breaker

```bash
curl -X POST http://localhost:9101/charge -d '{}' -H "Content-Type: application/json"
# порт 9101/9102/9103 — PayCore/FastPay/CryptoGate соответственно
```

Если мок отвечает нормально и быстро — деградация была именно на уровне
Toxiproxy/сети, не у "провайдера" как такового.

### 3. Была ли деградация симметричной или это накопленный эффект

```promql
app_provider_conversion_rate{provider="X"}
```
Смотри график за 30-60 минут — резкий обрыв (вертикальная линия вниз)
обычно означает внешнее событие (отключение сети, включённый Toxiproxy);
плавное снижение больше похоже на постепенную деградацию самого сервиса.

## Восстановление

**Если деградация была тестовой (Toxiproxy):**
```bash
# через меню
traffic_gen.py → 3 → 12. Снять ВСЕ деградации
```
Circuit breaker сам перейдёт в `half_open` через `cooldown_sec` (по
умолчанию 30 сек) после того, как провайдер снова начнёт отвечать
нормально, и закроется (`closed`) после нескольких успешных пробных
запросов.

**Если circuit breaker был разомкнут вручную (пункт меню 5):**
Он не восстановится сам — это сознательное ручное действие. Сбрасывается
только рестартом `traffic_gen.py`.

**Если деградация реальная (и это не лаба, а прод):**
Circuit breaker уже минимизирует ущерб сам — задача дежурного: следить
за `app_provider_conversion_rate`, ждать восстановления в `half_open`,
и параллельно связываться с провайдером/эскалировать инцидент на их
стороне, если она контролируется вами лишь частично.

## Проверка после восстановления

```promql
app_provider_circuit_state{provider="X"}   # должно вернуться к 0 (closed)
app_provider_conversion_rate{provider="X"}  # должно вернуться к норме (>0.9)
```
