# Runbook: High Payment Error Rate

**Алерт:** `HighPaymentErrorRate` — error rate платежей > 10% в течение 3 минут
**Приоритет по умолчанию:** P2. Переводи в P1, если error rate > 50% или растёт без остановки.

## Симптомы

- Панель "Error rate %" в Grafana растёт выше базового уровня (норма — единицы процентов)
- В Kibana Discover растёт число событий `event: "payment_failed"`
- Возможен сопутствующий алерт `ProviderCircuitBreakerOpen`, если причина — конкретный провайдер

## Первый шаг — отличить реальную проблему от шума

Прежде чем куда-то бежать, проверь: это устойчивый рост или единичный всплеск?

```promql
sum(rate(app_transaction_status_total{status=~"failed|timeout"}[5m]))
  / sum(rate(app_transaction_status_total[5m]))
```

Смотри на график за последние 15-30 минут — не на текущее значение. Алерт
специально настроен с `for: 3m`, то есть уже отфильтровал одиночный выброс;
если ты здесь — рост, скорее всего, устойчивый.

## Диагностика — по порядку

### 1. Один провайдер или все сразу?

```promql
app_provider_conversion_rate
```

- **Просел один провайдер** → это `provider-degradation.md`, иди туда — дальнейшие шаги отсюда не нужны.
- **Просели все разом** → продолжай ниже, это либо БД, либо сеть, либо общий сбой генератора/приложения.

### 2. Сеть между AppServer и DBHost

```bash
ping -c 5 10.10.10.12
```

Если есть потери пакетов или задержка резко выросла — проверь, не активна ли
сейчас деградация через Toxiproxy:

```bash
curl http://localhost:8474/proxies/postgres
```

Если там есть активные `toxics` — сними:
```bash
curl -X GET http://localhost:8474/proxies/postgres/toxics
# затем DELETE каждого найденного toxic, или через меню traffic_gen.py → 12. Снять ВСЕ деградации
```

### 3. Состояние БД

```sql
SELECT pid, now()-query_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC LIMIT 10;

SELECT * FROM pg_locks WHERE NOT granted;
```

Долгие/заблокированные запросы — частая причина каскадного роста ошибок
(транзакции не успевают расчитаться вовремя, settlement откладывается,
растёт и error rate, и latency одновременно).

### 4. Сам генератор/settlement-поток жив?

```bash
tmux attach -t traffic-gen
```
Проверь пункт меню 4 "Статус" — не остановлена ли генерация случайно, и не
завис ли settlement-поток (растущий `app_pending_transactions` без
уменьшения — плохой знак, см. `pending-stuck.md`).

## Восстановление

- Если причина — забытая деградация через Toxiproxy или принудительно
  разомкнутый circuit breaker: сними через меню `traffic_gen.py` → пункт 3 →
  12 "Снять ВСЕ деградации"
- Если причина — заблокированный запрос в БД: `SELECT pg_terminate_backend(<pid>);` для блокирующего PID
- Если причина в реальной перегрузке БД: проверь `pg_stat_database_numbackends` — не упёрлись ли в лимит соединений

## Эскалация

Если после снятия очевидных причин (Toxiproxy, форсированный CB, блокировки)
error rate не снижается за 10 минут — это может быть реальная деградация
на уровне ОС/ресурсов ВМ (проверь CPU/память по node_exporter дашборду).
В учебной лабе следующий шаг — просто перезапуск проблемного сервиса; в
реальной системе — эскалация на дежурного DBA/инфраструктурного инженера.
