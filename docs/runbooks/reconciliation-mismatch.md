# Runbook: Provider Status Mismatch (Reconciliation)

**Алерт:** `ProviderMismatchRateHigh` — более 15 расхождений статусов за 10 минут
**Приоритет по умолчанию:** P2. В реальной платёжной системе это не блокирует работу немедленно, но напрямую бьёт по финансовой отчётности — расхождения нужно сверять и закрывать, а не игнорировать.

## Что это значит

У нас записан один статус транзакции (`transactions.status`), а провайдер
в своём ответе (`provider_responses.external_status`) сообщил другой.
Это классический reconciliation-кейс в платёжных системах: наша система
может думать, что платёж прошёл успешно, а провайдер считает его
неудавшимся — или наоборот. Оба варианта требуют разбора, потому что
могут означать реальную потерю денег (в любую сторону).

## Симптомы

- Растёт `app_provider_mismatch_total`
- В Kibana Discover растут события `event: "provider_status_mismatch"`

## Диагностика

### 1. Это учебный сценарий?

```
traffic_gen.py → 3 → 4. Статус
```
Смотри строку "Mismatch: включен/выключен". Если включен — это ты
сознательно поднял уровень расхождений через пункт меню 7 для теста.

### 2. Найти конкретные расхождения через SQL

```sql
SELECT t.transaction_id, t.status AS our_status, pr.external_status,
       t.amount, t.provider_id, t.created_at
FROM transactions t
JOIN provider_responses pr ON pr.transaction_id = t.transaction_id
WHERE t.status != pr.external_status
  AND t.created_at > now() - interval '1 hour'
ORDER BY t.created_at DESC;
```

### 3. Какое расхождение опаснее — по направлению

```sql
SELECT
  t.status AS our_status,
  pr.external_status,
  count(*),
  sum(t.amount) AS total_amount
FROM transactions t
JOIN provider_responses pr ON pr.transaction_id = t.transaction_id
WHERE t.status != pr.external_status
  AND t.created_at > now() - interval '1 hour'
GROUP BY t.status, pr.external_status
ORDER BY total_amount DESC;
```

Расхождение **"у нас success, у провайдера failed"** опаснее — мы могли
засчитать деньги пользователю, а провайдер их фактически не провёл.
Расхождение в обратную сторону ("у нас failed, у провайдера success")
тоже плохо, но обычно менее срочно — деньги провайдер провёл, а мы
пользователю их не начислили, это раздражает, но не теряет деньги
компании напрямую.

### 4. Корреляция с деплоем или конкретным изменением (Kibana)

Если в логах есть события `event: "deploy"` (см. модуль 7 курса — логируй
момент деплоя отдельным событием), сравни временные метки в Kibana Discover:
```
event: "provider_status_mismatch" AND @timestamp: [now-1h TO now]
```
и отдельно:
```
event: "deploy"
```
Если расхождения начались сразу после деплоя — вероятная причина в самом
изменении (например, поменялась логика обработки ответа провайдера).

## Восстановление

**Если это учебный сценарий:**
```
traffic_gen.py → 3 → 12. Снять ВСЕ деградации
```

**Если расхождения реальные:**
Reconciliation в проде обычно не "чинится" одним действием — это процесс:
1. Выгрузить список расхождений (запрос из шага 2)
2. Для каждого — либо довериться нашему статусу, либо статусу провайдера
   (обычно решает бизнес-правило: чей статус приоритетнее для конкретного
   провайдера, или делается ручной запрос к API провайдера за актуальным
   статусом)
3. Скорректировать `transactions.status` вручную или через отдельный
   reconciliation-джоб
4. Задокументировать каждое исправление — это финансовые данные, изменения
   должны быть прослеживаемы (аудит)
